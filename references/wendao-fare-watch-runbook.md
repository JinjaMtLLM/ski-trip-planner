# 携程问道票面价巡检 · 操作手册（LLM 执行版）

> 面向「执行者 = LLM」而写。这里**没有脚本可跑**，只有步骤、判读规则和写盘约定。
> 配套工具只有一个：`scripts/wendao.js` 的 CLI（`--from/--to/--date`），职责仅限于把问题发出去、把原文带回来。

---

## 0. 为什么是文档而不是脚本

2026-10-26 起用 `tools/legacy/wendao_fare_watch.js` 做过 25 次小时级巡检，结论是**脚本化解析走不通**：

| 问题 | 实测 |
|---|---|
| 排版一天换几种 | ≥10 种（`**方案N｜…**` / `### 经X中转（3套）` / 无标记散文 / `### 中转兰州（…）` / `## 直飞方案`+`### CZ9001` / `### 9C6620-9C6166（最快中转）` / `- **第1段**` …） |
| 切分正确率 | 25 次里只有 7 次全对 |
| 典型错法 | 把「经兰州（5个）」一节并成 1 行 → 航班号取并集（凭空多 3 段、税翻 3 倍）、价格取最大、耗时取最大 |
| 残留脏值 | `中转城市` 列被写成 `方案：经兰州`（从段落标题里误抠） |
| 漏抓 | 2026-10-28 01:04 那次原文有 14 个方案，脚本只落 13 行（漏 3U8175） |

**而「原文里明摆着写了航班号、时刻、票面价」这件事是稳定的。** 所以：脚本只负责取原文，判读、抽取、写表、比价全部由 LLM 现场完成。排版变了，LLM 读得懂；脚本一变就得改代码。

## 1. 取原文（唯一一条命令）

```bash
cd D:/Project/other/ski-trip-planner
node scripts/wendao.js --from 阿勒泰 --to 深圳 --date 2027-01-03 --save out/fare-watch/raw
```

- **stdout** = 问道原文，原样，不加工 → 直接读它，不要另存再读。
- **stderr** = `[saved] out/fare-watch/raw/<ts>.txt` + 字数。
- 换航线/日期只改三个参数。`--query "…"` 可发任意问题（不落盘就别加 `--save`）。

**退出码**：`0` 成功 / `2` 配额 / `3` 鉴权 / `4` 网络或其他。

> 配额不足（退出码 2）：只报「本次配额不足，已跳过」。**不重试、不改用飞常准**（飞常准要积分且必须先问用户）。
> 鉴权失败（退出码 3）：报错并提示 `node scripts/doctor.js --probe`，本轮结束。

**每次运行 = 1 次问道配额。重跑会再扣一次，除非解析确实错了（那是本手册的 bug，不是数据的 bug），否则不要重跑。**

## 2. 先判 state，再读内容

读完原文，先回答一个问题：**这份回答里到底有几个「完整方案」？**
完整方案 = 同时具备「航班号」和「该方案自己的票面价」。

| state | 判据 | 处理 |
|---|---|---|
| `ok` | ≥1 个完整方案 | 正常抽取，写盘 |
| `no_inventory` | 0 个完整方案，且原文说「暂未检索到 / 无航班数据 / 尚未开放销售 / 没有符合条件的航班」 | **正常波动，不是故障**（凌晨 22:00–01:00 高发）。台账记 `state: no_inventory`，不写 fares.csv 行，汇报只说一句 |
| `odd` | 0 个完整方案，但原文**没有**明说无库存（例如只有一堆时刻没有价、或只给航司名） | 台账记 `state: odd`，`note` 写清原文实际说了什么，附原文首 200 字，交人判断 |

注意：**「没有直飞」不等于 no_inventory**，只要有中转方案就是 `ok`。反之「有直飞」也不代表方案完整。

## 3. 抽取：一个方案一行

### 3.1 字段表（写进 fares.csv 的 12 列，顺序固定）

| # | 列名 | 取值规则 |
|---|---|---|
| 1 | 查询时间 | 本次运行开始时刻 `YYYY/MM/DD HH:MM:SS`（Asia/Shanghai）。**整次运行共用同一个值**，不要逐行取不同秒 |
| 2 | 航线 | `AAT→SZX`（三字码 + `→`） |
| 3 | 出行日期 | `2027-01-03` |
| 4 | 航班组合 | 按航段顺序用 `+` 连接：`9C6620+9C6166`；直飞只写一个号：`CZ9001` |
| 5 | 中转城市 | **看第一段的落地机场，不看节标题、不看方案小标题**。1 段写 `直飞`；≥2 段写该机场所属城市简称（`兰州`/`西安`/`重庆`/`乌鲁木齐`）。**三种错源都要防**：① 节标题缺「经」字或写成「中转方案：经兰州中川（5个）」，抠出来是 `方案：经兰州`；② **节标题本身挂错**——2026-10-28 01:26 那次 `## 四、经西安中转` 下面第一个方案是 `9C6620-9C6166（经西安兰州…）`，正文第一段落地的是**兰州中川**，按标题记就错了；③ 方案小标题写「经西安兰州」这种两个城市都写上的，一律以正文第一段落地机场为准 |
| 6 | 航段数 | 航班号个数（1 = 直飞，2 = 一次中转，3 = 两次中转） |
| 7 | 票面价 | 该方案**自己**的票面价，纯整数（无千分位、无 `¥`、无「元」） |
| 8 | 税 | `140 × 航段数` |
| 9 | 含税总价 | 列 7 + 列 8 |
| 10 | 全程分钟 | 原文「全程约 X 小时 Y 分」→ `X*60+Y`；没写就用「首段起飞 → 末段落地」的时刻差（跨天要加 1440） |
| 11 | 到达 | 只认显式信息：**正文里**的 `01-04 00:05 落地` / `1月4日…抵达` → `1/4 到`；末段落地的日期等于出发日 → `当天到`；`次日/第二天` → `次日到`；`后日/第三天` → 按日期算成 `1/N 到`；都没有 → **留空** |
| 12 | 方案标题 | 该方案的小标题或首句，截 60 字。**英文逗号 `,` 必须换成中文顿号 `、`**（否则破坏 CSV 列） |

### 3.2 抽取铁律

1. **一个方案一行，绝不合并。** 「经兰州中川（5个）」下面是 5 行，不是 1 行。宁可多写。
2. **航班号只从该方案自己的描述里取。** 对比从句不算：「比同段 GS7558 方案贵」里的 GS7558 不是本方案的航班；「与 CZ9001 起降一致」里的 CZ9001 也不是。
3. **票面价取该方案自己的那一个，取第一个。** 遇到「区间 2090–3323」取 2090（这是最低价）；遇到「比它便宜 200 元」不要做减法。
4. **航段数 > 3 的，几乎一定是把汇总段当成了方案** → 丢弃，在台账 `note` 里记一句。
5. **直飞方案的航段数必须是 1。** 出现「直飞」标题却挂着两个航班号，说明那是代码共享/占位，按原文实际航班号记，不要标直飞。
6. 同一航班组合出现多次（不同段落重复列举），**只留票面价最低的一条**。
7. **不要为了凑数而编造。** 原文没给价就跳过，不估算、不跨方案借价。
8. ⚠ **节标题一律不可信，不只是「城市」那一列。** 2026-10-28 一天之内，分节标题的**到达形态**错了 5 次：「当日可达方案」节下混 4 条次日到达、「次日到达（需在1月4日落地）」节下 2 条实为 1/5 到、「当日到达」节下混次日 00:15 落地、「隔夜中转」节下混当天 23:00 落地。**节标题只当索引用，任何字段都以正文逐条为准**；节标题的计数同样不可信（曾写「（2个）」实为 3 条）。

### 3.3 四个高频误读

- **`01-03` 有两种身份，必须分清**：出现在正文航班描述里（`01-03 15:55起飞 → 01-04 00:05落地`）= 真实起降日期，可以用；出现在链接参数里（`ddate=2027-01-03`、`ddate=2027-01-03.2027-01-04`）= 查询参数，**不能拿来推断到达日**。
- 「15:55 起飞，00:05 抵达」没说次日，但 00:05 < 15:55 → 一定是次日，`到达` 填 `次日到`。
- **导语里的统计数不可信。** 2026-10-28 01:26 那次开头写「共查到14个方案，含2个直飞和12个中转」，但正文实际是 **3 直飞 + 11 中转 = 14**——散文里那句「另有厦门航空MF4939…票面价3805元」也是一条直飞，被导语漏算了。**以正文逐条为准，导语只当参考。**
- 散文里补的方案同样是方案。`另有XX航空XX航班，票面价XXXX元` 这种句式必须单独成行，不能因为它在段落中间就跳过（这正是脚本会漏的那一条）。
- **同一方案块里可能出现两套互相矛盾的时刻。** 2026-10-28 16:48 那轮，`- **起降时间**：01-03 15:40 → 20:50`（5h10、当天到）与同一块的 `#####` 链接里 `起飞 15:55 / 到达 00:05 / 飞行时间 8h10m` 同时存在。处置：**正文结构化字段优先于链接块**；两者差 >60 分钟时，按正文取值并在 `note` 里写「时刻矛盾，需人工核」。**不要默认较长的那套是对的**——那次 8h10 反而不合理（AAT→SZX 约 4,300 km，A320 纯飞行约 5.4h）。

## 4. 写盘：三个文件，不多建第四个

### 4.1 主表 `out/fare-watch/fares.csv`（长表，追加）

12 列，UTF-8 无 BOM，`\n` 换行，**不带引号**（靠 §3.1 第 12 列的「逗号换顿号」保证安全）。

用 Edit 在文件末尾追加本次全部行，一行一个方案：

```
2026/10/28 02:00:01,AAT→SZX,2027-01-03,9C7142+9C7680,兰州,2,2090,280,2370,1765,次日到,经兰州中川 9C7142+9C7680
```

**去重**：追加前先 `grep "<查询时间>" out/fare-watch/fares.csv`。已有同名时间戳说明重跑过 → 跳过写表，只在汇报里说明。

### 4.2 运行台账 `out/fare-watch/runs.jsonl`（每次一行，追加）

```json
{"at":"2026/10/28 02:00:01","route":"AAT→SZX","date":"2027-01-03","state":"ok","schemes":14,"direct":3,"coreHit":"4/5","minTotal":2370,"note":""}
```

- `schemes` = 本次落表行数；`direct` = 其中直飞条数
- `coreHit` = 五个核心方案（见 §6）本次返回了几个 `/5`
- `minTotal` = 本次最低含税总价，无则 `null`
- `note` = 一句话异常说明，没有就空串

### 4.3 快照 `out/fare-watch/latest.md`（覆写）

沿用现有版式：标题（航线 + 日期）→ 查询时间与口径 → 按含税总价升序的全量表 → 页脚口径说明。列：`# | 含税总价 | 票面 | 税 | 全程 | 到达 | 中转 | 航班 | 较上次`。
`较上次` 用上一次 `fares.csv` 里同航班组合的票面价对比，没有可比对象写 `—`。

## 5. 比价：先比覆盖，再比价

**铁律：两次 `schemes` 相差 ≥3 时，不许报涨跌。** 只报「本次覆盖不足（N 条 vs 上次 M 条），涨跌不可比」。

原因：问道的返回条数会随时间塌陷（实测 19:45 起五个核心方案只剩 1–2 个，22:58 只剩 1 个）。这时「最低价上升」是**假信号**——便宜的档位根本没返回。不看覆盖就把「没查到」读成「涨了」，是这个项目踩过最多次的坑。

`schemes` 接近时，只比**同一航班组合**的票面价，不同组合之间不直接比（一个 8h20 当天到、一个 29h 隔夜，价差是产品差异不是价格波动）。

---

## 6. 核心方案清单（覆盖率的锚）

这五个在 2026-10-26 ~ 10-28 的 26 次返回里出现频率最高，用来算 `coreHit`：

1. `9C7142+9C7680`（兰州，29h25，最便宜档）
2. `9C6620+9C7680`（兰州，32h10）
3. `9C6620+9C6166`（兰州，8h20，当天可接的最快档）
4. `9H8380+ZH9206`（西安，9h50）
5. `CZ9001`（直飞，8h10，价格锚）

**城市枚举不止四个**：`兰州` / `西安` / `重庆` / `乌鲁木齐` / **`成都`**（`ZH4006+HU7376`，8h05，是当天到达里最快的一档，2026-10-28 出现 7 次）。遇到新城市照实写，但只写城市名，**不要把括号里的备注（`（跨天衔接`、`等待约25小时`）带进这一列**——脚本期 48% 的行就是这么脏的。

清单会随时间漂移。若连续 5 次以上某方案不再出现，说明渠道库存变了，可在本文件里替换，并在 `runs.jsonl` 的 `note` 里写明换锚日期。

## 7. 汇报格式（给用户看的四条）

1. **本次状态**：state + 落表方案数 + `coreHit` + 有无直飞。
2. **含税最低 3 条**：航班组合、中转城市、全程耗时、票面价、含税总价、到达日。
3. **与上次对比**：先给覆盖判断，再给同组合涨跌（持平就写持平）。
4. **异常**：时刻矛盾、占位航班号（同刻同价的多家航司）、被丢弃的汇总段。

不写长篇分析。用户要的是「今天什么价、跟上次比变了没有」。

## 8. 禁止事项

- **不写解析脚本、不写验证脚本**。不建 `verified-*.md`、`*-recomputed.*`、`tmp/verify_*.js`。
- **不擅自改用飞常准**（消耗积分，必须先问用户）。
- **不重跑**（会再扣配额），除非本轮确实没拿到原文。
- **不在 fares.csv 里写没有原文支撑的推断值**（尤其到达日、中转城市）。
- **不动 `out/fare-watch/raw/`**：那是原文留档，只增不改。

| 型 | 长什么样 | 怎么读 |
|---|---|---|
| A | `**方案1（最快）｜经兰州中转，全程约8h20，票面价2420元**` + 正文 | 标题就是一个方案，价格在标题 |
| B | `### 经兰州中转（3套方案）` 下挂 `方案1：…票面价2170元。第一段9C6620…` | **节标题不是方案**，每个 `方案N` 各一行 |
| C | 整段散文，无「方案N」标记 | 按句号/分号切，凡「航班号 + 票面价」同现即一个方案 |
| D | `### 中转兰州（…）` / `## 中转方案：经兰州中川（5个）` | 同上，节标题只提供中转城市，**不要写进「中转城市」列** |
| E | `## 直飞方案（3个）` + `### CZ9001` + `- 价格：**¥3790**` | 每条 `###` 是一个方案，价格在子项里 |
| F | `### 9C6620-9C6166（最快中转）` + `第一段…；第二段…。全程约**8小时20分**，票面价**2240元**` | 标题里的 `-` 是航班号分隔符，不是减号；`第一段/第二段` 按顺序取号 |
| G | `- **第1段**：…` / `- **第一段**：…` | 数字可能是阿拉伯也可能是汉字 |
| H | `## 当天可达方案 / ## 跨日方案`（**按到达形态分节**） | 节标题的「当天/跨日」经常错（2026-10-28 错了 5 次），只当索引用，到达一律按正文时刻算 |
| I | `## 一、直飞方案（3个）` + `### CZ9001（南航直飞）` + `- **航班号**` / `- **起降时间**` / `- **全程耗时**` / `- **经济舱票面价**` 四行 + `#####` 链接块 | 最规整的一型，字段直接对应。**但链接块可能给出另一套时刻**（见 §3.3 末条），以正文为准 |
| J | `### 城市中转 航班号-航班号（备注）` / `### 阿勒泰-深圳（航班号-航班号）经XX` | 标题里城市和航班号混排，括号内是备注（`（跨天衔接`、`等待约25小时`）——**备注不进任何列** |

## 10. 已知的坑

1. **问道给不出含税价。** 追问税费它只回「工具未返回分项明细，无法拆分」。所以提问模板里主动写「只要票面价，税费我自己算」——这样它才肯把 10+ 个方案全列出来。
2. **「无直飞」的否定不可信。** 同一批方案里既出现过「1月3日无直飞」，也出现过 3 条直飞。
3. **「直飞」条目本身也可能是占位。** `CZ9001` / `3U8175` / `MF4939` 三家航司时刻票价几乎完全相同（15:55→次日 00:05，8h10，¥3790/3790/3805），而问道在另几次给的是 `CZ5482` 14:00→19:20、5h20。同一时刻三家共享代码是可能的，但「时刻全同、价差 15 元」更像渠道占位。**记录时照实记，汇报时提一句「直飞存在但形态存疑」。**
4. **覆盖率会塌陷。** 见 §5。
5. **凌晨 `no_inventory` 是常态。** 22:00–01:00 之间出现「暂未检索到航班数据」不要当故障，也不要换问法重试。
6. **税的口径**：`140 = 机建 50 + 长航线燃油 90`，与项目其他报告一致。AAT→URC 这类 500km 短段燃油实际只有 ¥20 上下，所以中转方案的含税估算**偏高 ¥60–120**，页脚要注明。要换口径用「短段 70/段」重算，但那只是本地算术，不改主表。

## 附录 A：标准提问模板

`node scripts/wendao.js --from <出发地> --to <目的地> --date <YYYY-MM-DD>` 内置的就是这段：

```
{年}年{月}月{日}日{出发地}飞{目的地}。
这一天能查到的方案都列一下，直飞和中转都要，只要票面价，税费不用管（我自己算）。

每个方案麻烦写成一段，里面包含：
- 每一段的航班号、几点起飞、几点落地、在哪个机场；
- 全程大概多少小时；
- 这个方案一个人的经济舱票面价多少元。

同一天不同中转城市的方案我都要看，别只挑最便宜的一两个给我。
```

三处不能删：
- **「只要票面价，税费不用管」** —— 删了它就只肯给一两个方案，或者反复解释税费。
- **「直飞和中转都要」** —— 删了容易只回直飞。
- **「别只挑最便宜的一两个」** —— 删了返回条数会掉到 2–3 条，覆盖率直接崩。

## 附录 B：历史产物位置
