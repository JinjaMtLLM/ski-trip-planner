# 计算模型

`scripts/planner.js` 的实现口径。改动前先读懂这里。

## 一、时间基准

所有时刻先转成「绝对分钟」：`dayNum(日期) × 1440 + 当日分钟`。这样跨日、跨月都可直接做减法，不需要特判。

日期一律按 **UTC 零点** 取整，避免本地时区导致日界漂移：

```js
dayNum = s => Math.floor(Date.parse(s.slice(0,10) + 'T00:00:00Z') / 86400000)
```

起飞日、落地日分开存（`date` / `arrDate`）。跨日航班的落地日写入 `arrDate`，同日的省略。

## 二、在场窗口

雪场只有在「人真的在雪场里」的时间段内才计入雪时：

```
进场 = 落地时刻 + 机场到雪场车程
离场 = 起飞时刻 − 值机提前量 − 机场到雪场车程
```

窗口 `[进场, 离场]`，两端都按绝对分钟算。窗口外的一切时间不计入。

例：起飞 06:40、提前 90 分钟、车程 120 分钟 → 离场 = 03:10，早于开门时间，当天雪时为 0。

## 三、逐日重叠求雪时

不做「首日 / 中间日 / 末日」的分段公式，而是逐日求交集，避免边界特判出错：

```
对窗口覆盖的每一天 t：
  日场 = 交集长度( [t+dayOpen, t+dayClose] , 窗口 )
  夜场 = 交集长度( [t+nightOpen, t+nightClose] , 窗口 )   // 夜场休息日跳过
```

- `日场小时 = Σ日场 / 60`
- `夜场小时 = Σ夜场 / 60`
- **总雪时 = 日场小时 + 夜场小时 × nightWeight**

这样自动获得几个正确行为：

- 深夜抵达（如 22:20 落地、次日 00:20 进场）能吃到最后一天的开场，而不是"少算一天"。
- 傍晚抵达能吃夜场尾巴（17:20 进场 → 18:00–21:00 全吃）。
- 早班返程（08:00 起飞 → 04:30 离场）当天雪时为 0，不需要额外规则。
- 夜场休息日自动跳过。

## 四、等效雪日

```
等效雪日 = 总雪时 ÷ 一个完整日场时长
```

一个完整日场 = `dayClose − dayOpen`（例如 7.5 小时）。夜场折半后，3 小时夜场只贡献 0.2 个等效雪日——这是刻意的，夜场体验与日场不等价，也是用户通常会指定的权重。

**元/日 = （含税机票 + 住宿）÷ 等效雪日**，报告里这一列就是排序依据。

## 五、请假天数

三段式，出发端与返程端分别判，再加中间跨越的工作日。三个时刻由用户给定，默认 `dayStart` 08:30 / `halfDayAt` 14:00 / `dayEnd` 20:00：

```
出发端（按起飞时刻）：
  周末出发 → 0
  起飞 ≥ dayEnd（默认 20:00）→ 0        // 下班后走
  起飞 ≥ halfDayAt（默认 14:00）→ 0.5
  否则 → 1

返程端（按 `arrDate` 的落地时刻）：
  周末落地 → 0
  落地 ≤ dayStart（默认 08:30）→ 0   // 还能赶上上班
  否则 → 1

中间日：出发日之后、落地日之前的工作日，每天 +1
合计 = 出发端 + 返程端 + 中间日
```

- 三个时刻必须满足 `dayStart < halfDayAt < dayEnd`，模型不做修正，配置写错直接报错。
- 出发端只用到 `halfDayAt` 与 `dayEnd`，返程端只用到 `dayStart`；改动其中任何一个都会重新划分各档的组合。
- 中转航班用**第一段起飞 / 末段落地**判定，因为请假看的是人什么时候离开和回来。
- 只保留合计值落在 `params.leaveBuckets` 里的组合，其余直接丢弃。
- 落点在周末但起飞在工作日的情况（如周五晚飞、周六到），出发端按工作日规则判——这是对的，人确实周五下班就走了。

## 六、费用

### 机票

```
含税机票 = 裸票价(去) + 裸票价(回) + taxPerSegment × (去程航段数 + 返程航段数)
```

- **航段数**：直飞 1、中转 2（可用 `seg` 覆盖）。
- **税费按航段各收一次**（国内航线规则）：中转单程 2 段、往返 4 段，等于直飞往返的 2 倍税费。
- `price` 写裸票价，税费由模型按航段叠加。

### 住宿

```
总晚数   = dayNum(返程落地日) − dayNum(出发日)
转机晚数 = 去程跨日 ? 1 : 0  +  返程跨日 ? 1 : 0
雪场晚数 = 总晚数 − 转机晚数
住宿     = 雪场晚数 × lodgingResort + 转机晚数 × lodgingTransit
```

三条边界：

1. **红眼不计住宿**：落地早于 `redEyeArrivalBefore`（默认 05:00）的航段，视为机上过夜，那一晚不收酒店钱。否则「18:15 起飞、次日 01:00 落地」会被误收一晚。
2. **只看跨日，不看中转时长**：同日中转不产生住宿，即使衔接 8 小时。
3. **雪场晚数用减法反推**，保证 `雪场晚 + 转机晚 = 总晚数` 恒成立，不会出现两边都不认领某一晚的情况。

深夜抵达（进场跨到次日 01:00）时，因总晚数按日期差算，那一晚仍计入雪场住宿——符合实际（凌晨入住同样要付当晚房费）。

## 七、去重

同「请假档 + 总雪时 + 总成本」的组合视为等价，只保留**出发更晚**（更省睡眠）的一条。这一步会把「早班机 + 晚班机同价同雪时」压成一条，表格不会出现看起来重复的行。

## 八、成本口径边界

**计入**：机票含税、住宿（雪场 + 转机）。

**不计入**：雪票、装备租赁、餐饮、地面交通、行李托运费。

「元/日」是机票加住宿的单价，在报告页脚列出未计入项，并在回复里点名 1–2 项对结论影响最大的。分母小（0 天、0.5 天档）时，未计入的固定支出占比更高。涉及廉航时把行李费按单程单件列出来，带雪具时按托运件计。

等效雪日用「一个完整日场时长」作分母，取值与用户确认的口径保持一致，中途不改。

## 九、敏感度检查

交付前对下面两个参数各扰动一次，对比各档最优解：

```bash
node scripts/planner.js cfg.json --out /tmp/a.html          # 用户给的口径
# 把 lodgingTransit 改为当地真实酒店价，另存 cfg2.json
node scripts/planner.js cfg2.json --out /tmp/b.html
# 把 taxPerSegment 换另一档，另存 cfg3.json 后再跑
```

把两三次的「各档最优」并列对比：

- 各次冠军一致 → 该档结论稳定，可以直接推荐。
- 冠军随参数变化 → 在回复里写明这一档的最优解取决于该参数，并给出两个取值下的结果。
