# 携程问道：自然语言查询模板

问道**不是**票价数据源，它是「一次问完一轮粗筛」的工具。实测一个 query 能同时返回：

- 3 个候选机场各自的航班、班次量级、最早/最晚落地
- 各机场的最低票面价与对应行程
- 各机场到雪场的驾车时长与里程
- 雪场本身的日场/夜场时间、雪季、雪道数
- 一句现成的取舍建议

所以**整个行程通常只调 1 次**（第 1 步的机场对比），最多再加 1 次（定稿前的执飞校验）。不要拆成「先问机场、再问骨架、再问营业时间」——那是三次调用换一次就能拿到的信息。

**缺了 `WENDAO_API_KEY` 时**：直接跳过粗筛，把候选机场列给用户让他选。**不要用飞常准补这一步**——它按「出发→到达」城市对扣积分（100 分/月），只留给第 3 步的详细检索。「先查一下这条航线有没有航班」这种试探，一次就是一积分。

精确票价一律走飞常准（`scripts/flight_query.js`）。**问道的结果不进 config。**

---

## 调用方式

原始 HTTP 接口，不封 CLI。key 从环境变量 `WENDAO_API_KEY` 读取。

```bash
curl -sS -X POST 'https://externalcallback.ctrip.com/skills/api/crew/skillhub/searchInfo' \
  -H 'Content-Type: application/json' \
  -d "{\"inputs\":{\"token\":\"$WENDAO_API_KEY\",\"query\":\"<你的自然语言问题>\"}}" \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.parse(s).result))"
```

响应是 `{ result, messages, state, events, error }`，**正文在 `result`**，其余字段是内部日志。

**HTTP 200 不等于成功。** `error` 为 `null` 但 `result` 可能只有一句「您的问题似乎与旅行服务无关」——必须判 `result` 内容，不能只看状态码。

## 写法四原则

一次能问多少，取决于**问的是聚合还是清单**。这是整套提示词的核心：

| 要 | 不要 | 原因 |
|---|---|---|
| 问**聚合量级**：几班、最早/最晚、价位区间 | 要**逐条航班清单** | 开放式枚举每类只给 2–4 条代表，问得越细丢得越多 |
| 用户口吻：「这几个我都要看，别只挑一个」 | 指令式：「硬性要求 / 禁止省略 / 禁止折叠」 | 触发内容审核，直接返回「与旅行服务无关」 |
| 一次只问**一个主题**（机场对比 or 执飞） | 混着问「直飞+中转+经停全量」 | 同主题内问得多不要紧，跨主题才掉质量 |
| 要求「**同时给出全程总耗时**」 | 只问「最低多少钱」 | 否则会拿 14 小时过夜中转的 400 元当最低价 |

最后一条是实测踩到的：问「深圳飞北京 12 月 11 日票价」，它答「400 元起」，但那个方案是 `CA3785 深圳 21:00 → 盐湖 23:35`，次日上午 `CA8624 → 大兴 11:00`，全程 14 小时、在运城过夜。**票价本身没错，但没有可比性。** 所以提示词里必须把「总耗时」和票价绑在一起问。

## 提示词 1：机场对比 + 骨架摸底（一次问全）

**用在**：第 1 步第 3 条。这是整个流程里唯一必需的一次问道调用。

```
我打算 <日期> 从 <出发城市> 飞去 <雪场所在区域> 的 <雪场名> 滑雪。能落地的机场我知道有这几个：
<机场A>、<机场B>、<机场C>。帮我比较一下这一天从 <出发城市> 飞这几个机场的情况：

每个机场分别说清楚——
1. 有没有航班，是直飞还是需要中转，大概几班；
2. 最早一班几点落地、最晚一班几点落地；
3. 最便宜的票大概多少钱，同时告诉我那个最便宜方案全程要多久
   （我不接受为了便宜在机场过夜十几个小时）；
4. 从机场开车到 <雪场名> 大概多远、要开多久。

另外 <雪场名> 本身的日场和夜场分别几点到几点、哪几天不开夜场，也一并说一下。

这几个机场我都要看，别只挑一个给我。
```

问句里已经埋了三个钩子，别删：

- 「同时告诉我全程要多久」——过滤掉过夜中转的低价陷阱；
- 「我不接受为了便宜在机场过夜十几个小时」——用户口吻的约束，比「硬性要求」有效；
- 「这几个机场我都要看，别只挑一个」——防止它只答最热门的那一个。

### 拿到结果后提取什么

| 提取项 | 可信度 | 下一步 |
|---|---|---|
| 有哪些机场可选 | 高 | 作候选起点；仍要自己想一遍有没有遗漏（邻近城市机场常被漏掉） |
| 有没有航班 / 是否需中转 | 中 | **否定判断必须核实**：「深圳没有直飞张家口」这类结论要用飞常准查一遍再采信 |
| 班次量级（约几班） | 中 | 只用于排除明显没航班的机场，不当精确值 |
| 最早 / 最晚落地 | 中 | 定骨架方向够用；精确时刻用飞常准 |
| 最低票面价 | 低 | 不含机建燃油，且常是超长中转。**只作量级**，精确比价用飞常准含税价 |
| 全程总耗时 | 中 | 用来识别「便宜但不可用」的方案，比票价本身更有信息量 |
| 机场 → 雪场车程 | 中 | 用 `amap_route.js` 取精确值；没有高德 key 时作降级值 |
| 雪场日场 / 夜场 / 雪季 | **低** | **必须用官方公示复核**。实测它把万龙写成「日场 08:00–21:30」，把夜场并进了日场——这个值直接决定雪时计算，错了排名全错 |

### 下一步

1. 入围的 2–3 个机场，用 `node scripts/amap_route.js` 逐个取精确车程（高德额度大，不用省）；
2. 雪场营业时间去官方公示核实，问道给的只当线索；
3. 把「车程 + 班次量级 + 价位量级」摆给用户选机场，骨架方向也一并确认；
4. 进第 3 步用 `flight_query.js --weekend --leave-days` 拿真实数据。

## 提示词 2：执飞校验

**用在**：第 3 步之后，对最终 1–2 个候选做确认。可选。

```
<日期> <航班号> 从 <出发地> 飞 <到达地>，这天执飞吗？计划几点起飞几点落地？
```

这是问道**唯一比飞常准更值得信的场景**——它在「这天飞不飞」上判断准确（实测与飞常准库存一致）。但下单前仍要用 `getBuyTicketUrl` 或航司官网复核。

只用它确认**已知航班号**，不要拿它发现新航班：它给的航班号偶发出错（实测把 EU9138 写成 EU9156、TV2438 写成 TV2454）。

---

## 字段可信度

| 字段 | 可信度 | 处理 |
|---|---|---|
| 是否执飞 | 较高 | 可采信，下单前仍要复核 |
| 机场是否有航班 | 中 | 肯定回答可用；**否定回答必须回查飞常准** |
| 时刻 | 一般准确 | 以飞常准为准 |
| 航班号 | **偶发出错** | 必须回查飞常准 |
| 票面价 | 量级可信 | 精确比价用飞常准含税价 |
| 中转方案覆盖 | **仅约 9%** | 不能用于枚举中转方案 |
| 机场→雪场车程 | 中 | 精确值用高德 |
| 雪场营业时间 | **低** | 官方公示为准 |
| 余票 | 不提供 | 用飞常准 `seats` |

## 轮次预算

| 场景 | 调用次数 |
|---|---|
| 常规行程 | 1 次（提示词 1） |
| 定稿前做执飞校验 | +1 次（提示词 2），可选 |
| 候选机场 ≥ 4 个、一次答不全 | 拆成两次，每次 2–3 个机场 |

问道按**日配额**，比飞常准（100 积分/月）宽松得多，但仍有三条限制：

- 同一 query 两次结果可能不同，**不可复现**——不要为同一件事反复问，问一次就把它榨干；
- 响应 21–57 秒，比飞常准（3 秒内）慢一个数量级，串行调用会明显拖长流程；
- 超配额返回配额类提示，不是报错中断。

所以：**粗筛随便问，定稿必须回飞常准。**
