# 路径枚举算法

`legs.js` → `enumerate.js` → `render.js` 三段。纯算法在 `graphcore.js`，不读不写文件，可离线测试。

## 为什么改成图枚举

老流程有一道人工闸门：从检索结果里挑几十条航班写进 `config.json`。问题是：

- **单边按价格排序会漏掉「略贵但时间好很多」的班次。** 便宜的 13:45 返程排在被选的 19:55 前面，但 19:55 能多滑 5 小时。
- **同一航班号在同一天可能有多条。** `9C7092+9C6540` 有「停 1.6 小时」和「停 25.6 小时」两种，按 `flight_nos` 去重会把好的那条吃掉。
- **漏斗有多窄看不见。** 481 条候选最后只进 32 条，保留率 7%，但没有任何地方提示「剩下 93% 里可能有更优解」。

图枚举把这道闸门去掉：只要边进了表，就会被穷举到。

## 数据模型

### 边（leg）

```js
{
  mode, from, to,            // 'flight' | 'rail' | 'taxi' | 'shuttle'
  depAbs, arrAbs,            // 班期边：绝对分钟（天 × 1440 + 分钟）
  durMin, waitMin,           // 即到即走边：车程 + 等车
  cost,                      // 含税总价
  entryMin, exitMin,         // 进站 / 出站时间
  scheduled,                 // 是否固定时刻
  ref, seg, stopMinutes, seats, note
}
```

时间一律用**绝对分钟**：`日期天数 × 1440 + 当日分钟`。跨日航班（落地 +1 天）因此不是特例，不需要 `arrDate` 这种补丁。

### 两类边的差别

| | 班期边 | 即到即走边 |
|---|---|---|
| 可行性 | `上一段到达 + 进站 ≤ 发车` | 上一段一到就走 |
| 时刻 | 固定 | `dep = 上一段到达`，`arr = dep + 等车 + 车程` |
| 例子 | 航班、高铁 | 打车、雪场接驳 |

进站/出站时间显式建模后，「落地到进场」不再靠一个含糊的总时长：

- 航班：进站 30 分钟（值机 + 安检 + 登机口），出站 20 分钟（下机 + 行李）
- 高铁：进站 15 分钟，出站 5 分钟

所以 `目的地机场 → 雪场` = 出站 20 + 车程 57 = 77 分钟，而不是拍一个 `toResortMinutes: 85`。

## 五步

### 1. 建路径表（`legs.js`）

- 航班：读飞常准缓存，`cost = 票价 + 实际机建燃油`。停留超过 `maxStopMinutes`（默认 480）的中转直接剔掉。

**同城多机场**：机场代码从 `legs[1].segments[]` 里取——`segments[1].dep_airport` 是出发机场，最后一段的 `arr_airport` 是到达机场。`buildSql()` 必须显式 select 这两列（`dep_ap` / `arr_ap`），只取扁平列的话机场信息就丢了。这解决了代码共享航班的误判（同一航班挂多家公司、实际落地机场与航司归属不一致）。

只有两处还要靠推断，都写在 `legs.js#airportOf()` 里：① 升级前落盘的旧缓存没有机场列；② 城市码（`network.json#cityCodes`）按航司映射表 `network.json#airportOfAirline` 落到具体机场，无映射时用 `default` 兜底；两者都没有就直接报错，不猜。

**同时刻去重**：同一 `(起飞时刻, 到达时刻, 中转次数)` 常有 3–5 条代码共享重复（同一航班挂 CZ/MF/KN 多个号）。`buildSql()` 用 `QUALIFY ROW_NUMBER() ... PARTITION BY` 只留最便宜的一条——否则北京这种干线两天并查必撞 200 行上限，被截断的反而是有价值的尾部日期。

- 高铁：`network.json`（case 目录里的路径表，`networkFile` 指定）里的时刻表按 case 的日期范围逐日展开。
- 打车/接驳：双向各一条，即到即走；反向边的备注会翻转方向（`flipNote`）。

### 2. 穷举（`dfsPaths`）

去程从出发地 DFS 到雪场，返程从雪场 DFS 回出发地。约束只有三条：

- 时间能接上（见上表）
- 不重复经过同一节点（防绕圈）
- 段数 ≤ `maxLegs`（默认 5）

没有「只保留最便宜的 10 条」这类阈值——那等于把人工闸门换个地方放。

### 3. 同键剪枝（`prunePaths`）

按 `(年假档, 日期, 关键时刻, 夜间状态)` 分组，每组只留最便宜的一条：

- 去程键：年假档 + 出发日 + **到场时刻** + 夜间状态签名
- 返程键：年假档 + 落地日 + **离场时刻** + 夜间状态签名

正确性：同键的两条路径，下游的雪时、住宿、返程代价完全相同，只有交通费不同。所以贵的被便宜的**严格支配**，剪掉不影响最优解。

`夜间状态签名` 是必须的：两条路径可以到场时刻和价格都一样，但一条红眼在机上过夜、另一条在机场酒店过夜，住宿费不同。

### 4. 返程重定时（`retimeReturn`）

这一步不做会毁掉整个枚举。

DFS 只能按最早可行时刻铺边。返程的第一段是打车（即到即走），于是每条返程路径都从「时间窗第一天 00:00 打车去机场」开始 —— 所有人离场时刻相同，剪枝后只剩个位数，全部被判定为「时间冲突」。

但对返程而言：**离场越晚，雪时越长，花费不变**。所以「刚好赶上第一段班期交通」严格最优。实现是把开头连续的即到即走边倒着推：

```
taxi.dep = flight.dep − flight.entryMin − taxi.durMin − taxi.waitMin
```

这样每条返程路径的离场时刻就是它真实能实现的时刻，差异回来了。

### 5. 配对与计算

去程 × 返程笛卡尔积，只留 `返程离场 > 去程到场`，然后逐对算：

```
交通费 = Σ 边花费
住宿   = 雪场晚 × lodgingResort + 中转晚 × lodgingTransit
雪时   = 到期窗口 ∩ 日场 / 夜场营业时间（夜场 × nightWeight）
年假   = 去程端 + 返程端 + 中间整工作日
元/雪日 = (交通费 + 住宿) ÷ (雪时 ÷ 一个完整日场)
```

**住宿按夜间采样点判定**（默认每天 03:00）：

- 在雪场 → 雪场晚
- 在某个机场/车站，且停留 ≥ `terminalWaitFreeMin`（默认 240 分钟）→ 中转晚
- 正在车上/机上，或停留 < 240 分钟（候车）→ 0

红眼航班因此自动免住宿，不需要「红眼落地不计住宿」这种特例规则。

## 口径

下表的「代码默认」只有前两行真的写死在脚本里，其余都从 `case.json` 读、缺了就报错——没有静默兜底。

| 项 | 代码默认 / 取值 | 说明 |
|---|---|---|
| `maxStopMinutes` | 480 | 超过的中转航班边直接剔除 |
| `terminalWaitFreeMin` | 240 | 短于此时长的候车不订酒店 |
| `nightBoundary` | `03:00` | 夜间采样点 |
| `lodgingResort` | 用户给定（示例 300） | 雪场每晚 |
| `lodgingTransit` | 用户给定（示例 80） | 中转城市每晚；按当地实际住宿价填，当天往返中转可以远低于雪场价 |
| `leave.dayStart / halfDayAt / dayEnd` | 必填（示例 `10:00 / 13:30 / 19:30`） | 出发端看起飞、返程端看落地；通用示例是 `08:30 / 14:00 / 20:00` |

档位不在这张表里：配对完成后取 `组合里出现过的所有年假天数` 去重排序，每档各取前 `--top`（默认 30）名。

## 已知局限

- **高铁时刻表不是 API。** 来自 12306 与第三方聚合站，雪季加开的 D9261–D9270 未逐趟录入。出行前必须复核。抓取用 `scripts/rail_12306.js`：它默认 1 QPS 节流（`--qps` 可调），把限流识别成 302 或「200 + HTML」，预售期外（15 天）直接拒绝——连发是唯一会踩雷的用法。
- **打车费是估算。** 按里程 × 单价 + 起步 + 高速，实际以网约车报价为准。
- **一个航班行是一个边。** 两段中转的航班，其内部停留时刻看不到，所以中途 8 小时在机场过夜会被算成「在路上」（0 住宿）。用「长中转 N h」标记提示用户。
- **余票不参与可行性判断。** 只有 1 张票的方案和 9 张票的方案排在一起。
- **纯价格排序不考虑舒适度。** 所以每条行程都带标记，标记在表格「备注」列可见；「各档最优」每档只给唯一解，长中转的替代方案由用户按备注列自行取舍。
