# 问答脚本

凭据检查完成后三轮提问，每轮最多 3 题。用户已经说过的信息不要重复问；能从上下文推断的先推断，然后在下一题里顺带确认。

重要：**所有数值都必须落到用户的明确回答上**。选项里的建议值只是「让用户少打字」，不代表可以默认采用。

---

## 第零轮：凭据（静默检查，缺失才问）

先跑 `node scripts/doctor.js`（零成本，只读配置），三个凭据都在就不提这件事，直接进入第一轮。

缺 key 时，把对应引导原样转给用户，一次只问一个。**必选那个一定要给「不配置」的选项**——用户有权拒绝，拒绝就走手动录入，不要反复劝：

```
header: 航班数据
question: 查航班要一个飞常准 MCP 的 key，在 https://cmcp.variflight.com/ 申请（微信扫码即可）。
          拿到后一条命令就能配好：
          VARIFLIGHT_MCP_KEY="你的 key" node scripts/mcp_config.js --write
          配完在连接器管理里把它设为信任（Trust）才生效。
          不想配也可以：我按你给的航班手动录入，照样能算出各档排名，只是没有自动比价。
options:
  - 我去申请，稍后给你
  - 我把 key 发你，这次直接用
  - 我不配置，手动给航班（走手动录入）
```

高德是**兜底**项，只在问道给不出车程时才需要，不要主动推销：

```
header: 车程（兜底）
question: 问道没给出可靠的驾车时长。要精确算「元/雪日」，车程是个关键值。
          有高德 Web 服务 key 的话（https://console.amap.com/dev/key/app，服务平台选「Web服务」，
          开通「地理编码」「驾车路径规划」）我直接查；没有就告诉我单程大概多少分钟。
options:
  - 我设置 AMAP_API_KEY
  - 直接告诉你分钟数（我来给）
  - 按你估算的先算，报告里标注为估算
```

问道的 key 是**建议配置**的——它是粗筛的唯一来源。但缺了也不卡流程，只是要改成让用户自己选机场：

```
header: 粗筛（建议配置）
question: 建议配一个携程问道的 token：我可以一次问完几个候选机场的航班、票价量级、车程和雪场营业时间，
          用它来定机场和行程骨架。它按日配额、不占飞常准积分，一轮就够。
          在 https://www.ctrip.com/wendao/openclaw 申请，按 export WENDAO_API_KEY='你的 token' 设置。
          没有也能继续，我直接把候选机场列给你选——但不会拿飞常准去代查，那样太费积分。
options:
  - 我设置 WENDAO_API_KEY
  - 没有，直接列候选机场给我
```

要点：

- 先讲用途（这个 key 换到什么数据），再给变量名和申请地址。
- 用户把 key 发在对话里时，用内联环境变量只传给本次进程，之后不再复述 key 的内容。
- 用户选「我不配置」时**不要劝**，直接跑 `node scripts/doctor.js --manual` 拿清单，转入手动录入（`references/manual-flights.md`）。没有航班数据确实算不出组合，但用户可以自己给航班——这一步不是死路。

## 第一轮：目的地、机场选择与接驳（必须先完成并确认）

需要拿到：

| 项 | 问法 | 备注 |
|---|---|---|
| 雪场全名 | 「你打算去哪个雪场？」 | 同一城市常有多个雪场，必须确认到具体度假区 |
| 出发城市 / 机场 | 「从哪个城市出发？有偏好的机场吗？」 | 一线城市多机场，邻近城市可能是隐藏选项 |
| 出行人数 | 只影响总价，不影响单价，可放在后面顺带问 | |

拿到雪场名称后自己去查（不要问用户）：

| 要拿到 | 怎么拿 |
|---|---|
| 雪场周边有哪些可用机场 | 自行判断，结合航线覆盖而非单纯距离 |
| 各机场有无航班、班次量级、最早/最晚落地、票价量级、到雪场车程、雪场营业时间 | **一次问道调用全拿**（`references/wendao-prompts.md` 提示词 1），不要拆成「机场 → 骨架 → 营业时间」三轮 |
| 各机场的驾车用时（含预留） | **先用问道给的值**（预留 +30%，标 `wendao`）；只有它没给、明显不合理、或两个机场车程差在 30 分钟内时，才跑 `node scripts/amap_route.js` 取精确值（标 `amap`） |
| 日场 / 夜场营业时间、夜场休息日（权威值） | 官方公示 |

问道给的是量级，不要写成精确数字；车程是精确值，可以写死。营业时间以官方公示为准，问道那版只当线索——它会把夜场时间并进日场。问「最低票价」时必须同时问「全程总耗时」，否则会拿过夜中转的低价当基准。

**候选机场 ≥ 2 个时，先把预查结果摆出来让用户选**，用 AskUserQuestion：

```
header: 到达机场
question: <雪场> 周边有这几个机场，样本日 <日期> 的情况（车程已含预留）：
          <机场A>　车程 XhXX　进场 <HH:MM>　约 <N> 班　价位 <区间>
          <机场B>　车程 YhYY　进场 <HH:MM>　约 <M> 班　价位 <区间>
          选哪个作主选？
options:
  - <机场A>（车程短）
  - <机场B>（航班多/票价低）
  - 两个都纳入，让方案自己比
```

用户选「都纳入」时，后续检索按机场逐个跑，合并到同一份报告。

**然后必须输出这张确认卡**，用 AskUserQuestion 让用户点确认：

```
行程骨架确认
─────────────
出发      <城市> <机场名>（<三字码>）
到达      <机场名>（<三字码>）        ← 多机场时逐行列出
雪场      <雪场全名>
单程车程  驾车 <X> 分钟，加 <Y> 分钟预留 → 按 <X+Y> 分钟计
日场      <起>–<止>（<Z> 小时）
夜场      <起>–<止>，按 <权重> 折算；<周几>不开放
─────────────────
以上无误就开始算行程？
```

选项给：`确认无误` / `车程要改` / `营业时间要改` / `换个雪场`。

> 车程预留的默认策略：**+20% 且至少 +15 分钟**。若用户提到冬季山路、夜间抵达、需要装防滑链，改成 +30% 以上，并在卡里写明。多机场且车程不同时，按最长的一段计，并在卡里注明。

## 第二轮：时间范围与预算（3 题）

### 题 1　出行时间范围

```
header: 出行时间
question: 这次想比较哪几个时间段？
options:
  - 一个周末（只出 1 份方案）
  - 两个相邻周末（可横向对比，推荐）
  - 连续假期（春节/元旦等，行程可更长）
```
两个以上时，要求用户给出具体日期，或自己按「第 N 个周末」推算后**回读给用户确认**（周末定义、是否含周五晚出发要说清）。

### 题 2　住宿预算

```
header: 住宿预算
question: 住宿按每晚多少算？雪场和转机城市分开给。
options:
  - 雪场 <A> / 转机 <B>（经济型）
  - 雪场 <C> / 转机 <D>（舒适型）
  - 雪场 <E> / 转机 <F>（度假型）
```

**两个价格分开问**：转机城市机场周边的过夜价与雪场差异较大，各自独立取值。

如果用户只给了一个数，追问：「这个价是雪场的还是转机城市的？另一个按多少算？」

### 题 3　最多请几天

```
header: 年假上限
question: 最多能请几天年假？（决定航班查到多宽的日期窗口）
options:
  - 最多 1 天（含只请半天的情况，推荐）
  - 只能 0 天（周末往返）
  - 最多 2 天
  - 最多 3 天（`--leave-days` 的上限）
```

这个数**不筛结果**：只用来决定航班查询窗口（周末 ± (天数+1)），报告会把组合里出现的所有年假档都列出来，每档各取最优 30 条。所以别追问「想比较哪几档」——都算。

## 第三轮：口径确认（3 题）

### 题 1　税费口径

```
header: 税费
question: 机票税费按每航段多少算？（机建 + 燃油合计）
options:
  - ¥150 / 航段（常见口径）
  - ¥90 / 航段（燃油低位）
  - 你帮我查实时标准
```

说明**税费按航段计收**：中转单程 2 段、往返 4 段。

### 题 2　请假口径

三个时刻各管一件事，全部要落到用户回答上：

| 字段 | 管什么 | 默认 |
|---|---|---|
| `dayStart` | 上班时刻。返程落地不晚于此值 → 0 天 | `08:30` |
| `halfDayAt` | 半天分界。出发早于此值 → 1 天，晚于此值 → 0.5 天 | `14:00` |
| `dayEnd` | 下班时刻。出发不早于此值 → 0 天 | `20:00` |

```
header: 请假口径
question: 请假按哪几个时刻折算？默认「上班 08:30 · 半天分界 14:00 · 下班 20:00」，
          即工作日 14:00 前起飞请 1 天、14:00–20:00 起飞请 0.5 天、20:00 后起飞不请假；
          返程 08:30 前落地不请假，更晚落地请 1 天。按这个算吗？
options:
  - 沿用默认（08:30 / 14:00 / 20:00）
  - 朝九晚六（09:00 / 14:00 / 18:00）
  - 三个时刻我自己给
```

用户选「我自己给」时，按 `dayStart` → `halfDayAt` → `dayEnd` 逐个问，每个都要拿到 `HH:MM`。拿到后回读一遍三个时刻与对应的折算规则，请用户确认再写入 `params.leave`。

三个值必须满足 `dayStart < halfDayAt < dayEnd`；不满足时说明当前矛盾在哪，请用户重新给。

`dayStart` 决定返程能不能不请假：按落地后实际能到岗的时刻取，值越晚可选的 0 天返程越多。

### 题 3　（可选）附加约束

```
header: 附加约束
question: 有没有必须满足的条件？
options:
  - 无，只看性价比
  - 只要直飞（不接受中转）
  - 必须带雪具（要考虑行李费）
  - 单程总耗时不超过 X 小时
```

「必须带雪具」不改变模型，结论里单列行李托运费。

## 何时停止提问

三个条件都满足就可以开始跑数：

1. 行程骨架已确认
2. 住宿两个价、税费单价、最多请假天数（只用于铺查询窗口）、请假三时刻（`dayStart` / `halfDayAt` / `dayEnd`）都有明确数值
3. 平票时的取舍偏好已知（或用户明确说不在意）

## 用户答不上来时

- 「大概多少」→ 给 2–3 个具体数字让用户选。
- 「你看着办」→ 说「我先按 A 算，报告里会标注这是假设值，你可以随时让我改成 B」，然后在报告头部标注该值为假设。
- 完全没有概念（比如从没去过该雪场）→ 先查官方公示再复述给用户确认；拿不到就停下来问。
