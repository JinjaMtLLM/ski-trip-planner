# 问道抽取契约（NL → 结构化）

> 一句话：**subagent 只负责「把原文里的数字搬进 schema」，不负责算、不负责判断对错。**
> 算和判断由确定性脚本做。这样任何一步出错都能定位到唯一环节。

---

## 0. 为什么要有契约

旧链路里 LLM 同时做五件事：读原文 → 判读 → 算税 → 拼 12 列 CSV → 算覆盖率 → 写报告。
任何一处错，事后无法判断是「读错了」「算错了」还是「写错了」。

新链路把职责切开：

| 环节 | 谁做 | 输入 | 输出 | 可否重做 |
|---|---|---|---|---|
| 取原文 | `scripts/wendao.js` CLI | 航线+日期 | `raw/<ts>.txt` | 是（耗配额） |
| **抽取** | **subagent（LLM）** | raw + 本契约 | `extracted/<ts>.json` | **是（零配额，可反复重跑同一份 raw）** |
| 校验 | `scripts/validate_extract.js` | json + raw | 通过/拒绝 + 原因 | 是（零成本） |
| 算术 | 同上（脚本） | json | 补 `tax` / `total` / `durationMin` | 是 |
| 写盘 | 同上（脚本） | 校验后的 json | `fares.csv` / `runs.jsonl` / `latest.md` | 是 |

**抽取是唯一有判断的环节，也是唯一需要 LLM 的环节。** 其余全部确定性。
抽取可以拿同一份 raw 重跑任意次——这是它最大的好处：**可以测一致性**。

## 1. Schema（v1）

```json
{
  "schemaVersion": 1,
  "queryTime": "2026-10-28T19:55:07+08:00",
  "route": { "from": "AAT", "to": "SZX", "fromCity": "阿勒泰", "toCity": "深圳" },
  "travelDate": "2027-01-03",
  "state": "ok",
  "declaredCount": 10,
  "schemes": [
    {
      "flights": ["9C6620", "9C6166"],
      "hub": "兰州",
      "hubBasis": "兰州中川T3",
      "segments": [
        {
          "flight": "9C6620",
          "depDate": "2027-01-03", "depTime": "15:55", "depAirport": "阿勒泰雪都",
          "arrDate": "2027-01-03", "arrTime": "19:00", "arrAirport": "兰州中川T3"
        },
        {
          "flight": "9C6166",
          "depDate": "2027-01-03", "depTime": "20:45", "depAirport": "兰州中川T3",
          "arrDate": "2027-01-04", "arrTime": "00:15", "arrAirport": "深圳宝安T3"
        }
      ],
      "fare": 2240,
      "currency": "CNY",
      "totalDurationText": "8小时20分",
      "arriveDateSource": "derived",
      "evidence": "### 9C6620-9C6166（春秋航空，当日到达）…票面价 2240 元/人"
    }
  ],
  "unparsed": [],
  "warnings": []
}
```

### 字段规则

| 字段 | 必填 | 规则 |
|---|---|---|
| `queryTime` | ✓ | ISO 8601 带 `+08:00`。**整份 JSON 共用一个值**，取本次运行开始时刻 |
| `route.from/to` | ✓ | IATA 三字码大写 |
| `travelDate` | ✓ | `YYYY-MM-DD`，出发日 |
| `state` | ✓ | 枚举：`ok` / `no_inventory` / `odd` |
| `declaredCount` | ✓ | 原文导语自称的方案数；**原文没说填 `null`**。它只用来和 `schemes.length` 比对，不作数 |
| `schemes[].flights` | ✓ | 按航段顺序的航班号数组，**不要写成 `A+B` 字符串** |
| `schemes[].hub` | ✓ | 枚举：`兰州`/`西安`/`重庆`/`乌鲁木齐`/`成都`/`直飞`/`其他:<城市名>`。**只看第一段的 `arrAirport`**，不看节标题 |
| `schemes[].hubBasis` | ✓ | 判定依据的机场名原文（如 `兰州中川T3`）。直飞填 `null` |
| `segments[]` | ✓ | 每个航段一条，字段全部来自原文，**没写就 `null`，不许推** |
| `segments[].depDate/arrDate` | ✓ | `YYYY-MM-DD`。原文只写「次日/后日」时，**按 `travelDate` 换算后填**，并在 `warnings` 里记一条 |
| `fare` | ✓ | 整数，人民币，**该方案自己的票面价**。不确定填 `null`，不要填别人的 |
| `totalDurationText` | ✓ | 原文的时长原话（`约8小时20分` / `8h20m`）。**不要换算成分钟**，换算归脚本 |
| `arriveDateSource` | ✓ | `explicit`（原文写了日期）/ `derived`（原文只写「次日/后日」，换算得出）/ `null`（无依据） |
| `evidence` | ✓ | 该方案的原文片段，≤120 字，能定位到具体块 |
| `unparsed` | ✓ | 原文里看到但没能抽成方案的片段（一句话说明）。**宁可报，不许静默丢** |
| `warnings` | ✓ | 发现的矛盾（节标题挂错城市、同块两套时刻、导语计数不符等） |

### 不出现的字段（故意）

`tax` / `total` / `durationMin` / `coreHit` / `minTotal` / `segs` / `arriveLabel` ——
**全部由脚本算**。LLM 填这些只会引入算术错误，而算术错误是最容易避免的错误。

---

## 2. 三条铁律

1. **不许猜。** 原文没给的值填 `null`。`fare` 为 `null` 的方案直接不产出（进 `unparsed`）。
   schema 里允许 `null` 就是为此，不要为了「填满」而编造。
2. **不许静默丢弃。** 抽不出来的东西写进 `unparsed`。原文说有 14 个方案而你只抽到 12 个，`warnings` 里必须写「导语称 14，实抽 12」。
3. **只搬事实，不做换算。** 时长写原话，日期照原文，票价照抄。所有计算归脚本。

## 3. 抽取器 prompt（可直接用）

```
你是「问道原文 → JSON」的抽取器。只做一件事：把下面这段自然语言里的航班方案搬进给定 schema。
不做算术，不做推断，不做总结。

【输入】
- schema 定义：references/wendao-extract-contract.md §1
- 原文：<raw 文件内容，或文件路径>

【硬性规则】
1. 一个方案一条，绝不合并。「经兰州中转（5个）」下面就是 5 条。
2. 中转城市看第一段 arrAirport 属于哪个城市，不看节标题、不看小标题。
   节标题的「当日到达 / 隔夜 / 经X中转」全部不可信，一天内会错 5 次。
3. 散文里「另有XX航空XX航班，票面价XXXX元」也是独立方案，必须单独成条。
4. fare 必须是该方案自己的价。同一段里出现多个价格时，取紧跟本方案航班号的那个。
5. 时长写原文原话，不换算成分钟。
6. 原文只写「次日/后日/第三日」时，按 travelDate 换算成 arrDate，arriveDateSource 填 "derived"。
   原文写了具体日期时填 "explicit"。都没有填 null。
7. 抽不出来的（有航班号但没价、时刻矛盾无法判断）写进 unparsed，一句话说明。
8. 发现的矛盾写进 warnings：节标题与正文不符、同块两套时刻、导语计数与正文不符。
9. 不写 tax / total / durationMin / segs —— 这些由脚本算。

【输出】
只输出 JSON，不要 markdown 代码块包裹，不要任何解释文字。
```

## 4. 校验与写盘（`scripts/validate_extract.js`）

脚本按顺序做 6 件事，任何一步失败即拒绝写表：

| # | 检查 | 失败处置 |
|---|---|---|
| 1 | JSON 可解析、`schemaVersion === 1` | 拒绝 |
| 2 | 必填字段齐全、类型正确、枚举合法 | 拒绝，列出缺哪个 |
| 3 | `flights.length === segments.length` | 拒绝 |
| 4 | **证据校验**：每个航班号、`fare` 能在 raw 里找到，且 `fare` 与本方案**全部航班号落在同一个方案块**内 | 拒绝（防编造/防串价） |
| 5 | 算术补全：`segs` / `tax` / `durationMin`（从 `totalDurationText` 或时刻链）/ `total` / `arriveLabel` | 自动补，不拒绝 |
| 6 | 写盘：`fares.csv` 追加、`runs.jsonl` 追加、`latest.md` 覆写 | — |

校验失败 → JSON 落到 `quarantine/<ts>.json`，**不污染主表**，退出码 1。

## 5. 怎么证明抽取器可靠

**同一份 raw 重跑 N 次，比对输出。** 这是脚本化时代做不到的——旧解析器同一份输入永远给同一份输出，测不出「理解是否稳定」。

判据：
- `flights` 集合完全一致
- 每条 `fare` 完全一致
- `hub` 完全一致
- `arriveDate` 允许 `explicit` 与 `derived` 互换，但日期值必须一致

不一致的方案列为「争议项」，人工看。**这比任何字符串校验都强**，因为它验的是理解，不是字面匹配。

2026-10-28 已有的弱证据：01:26 与 01:28 两份**排版完全不同**的原文（一份散文补方案、一份每段自带日期），两次独立判读的 14 条航班组合与票面价逐条相同。说明规则对排版不敏感。

## 6. 与证据校验器的关系

- `validate_extract.js` 的第 4 步 = 硬证据校验（航班号 + 票面价 + 同块归属），**在写表前**拦截
- `scripts/verify_fares.js` = 对已写入的主表做**事后审计**，可跑全历史
- `scripts/negtest_gate.js` = 校验门**自己**的回归测试
- 三者共用同一套证据规则，但用途不同：闸门 / 审计 / 自证

**校验器只能证明「存在」，不能证明「归属」。** 归属靠 §5 的重跑一致性，以及 `evidence` 字段的人工抽检。

### 6.1 价格归属判据：块内共现（两次负向测试的结论）

判据演进过三轮，每轮都是被负向测试打回来才改的：

| 判据 | 漏在哪 | 结果 |
|---|---|---|
| 「任一航班号附近」 | 共享首段的方案互相串价（9C7142+HU7851 抄 9C7142+9C7680 的 2090） | 漏检 |
| 「全部航班号的最小跨块窗口 + ±400 字符容差」 | 航班号在标题行也出现，递归会把上一块首段和下一块首段配成一对；上一块末尾的 `- 价格：**¥4260**` 距本块标题仅 12 字符，容差直接跨块 | 漏检 |
| **「同一方案块内共现」** | — | 拦住 |

实现要点：
- 按 `#`/`##`/`###` 切块，**`#####` 链接子块并入父块**——否则 `**票面价**` 在子块之前、`- 价格` 在子块之内，会被切成两半
- 严格档：存在某个块同时装下本方案全部航班号 → 价格必须也在这个块里
- 宽松档：没有任何块能装下全部航班号（散文式排版）→ 退回 ±80 字符紧窗口。**实测 494 行历史数据全部走严格档，宽松档一次没被触发**，只是安全网

### 6.2 校验门必须自证

校验器报「100% 通过」证明不了任何事——一个什么都不查的校验器也是 100% 通过。所以有 `scripts/negtest_gate.js`：从**最新一份真实抽取结果**现场生成 10 类注入错误（编造价 / 编造航班号 / 航段数不符 / 串价 / 脏中转城市 / 非法枚举 / 自相矛盾状态 / 错 schema / 越界票价 / 缺字段），每类都必须被拒绝。

- 用例从真实数据现场推导，**不硬编码航班号**，换航线换日期照样能跑
- 改完任何证据逻辑后必须跑，10/10 拦住才算过
- 当前：**10 拦住 / 0 漏过**
