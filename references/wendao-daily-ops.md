# 每日巡检编排（3 班次 / 天，达标即早退）

> 每小时模式靠「下一小时再来一次」兜底；每天 1 次没有这个退路，**单次失败当天就没了**，
> 而票价是当日快照，明天问同一天的价格已经变了。
>
> 本方案：**每天调度 3 班（09:00 / 12:00 / 16:00），班次内只做短重试，覆盖不足交给下一班，
> 任一班达标后其余班次由脚本 early out**。可靠性来自调度冗余，不来自单次长重试。

---

## 0. 实测基线（2026-10-28，19 批 / 225 行）

| 层级 | 判据 | 成功率 |
|---|---|---|
| L1 传输 | 拿到非空原文 | 19/19 = **100%** |
| L2 判读 | 抽出 ≥10 条方案 | 16/19 = **84.2%** |
| L3 覆盖 | coreHit ≥ 4/5 | 15/19 = **78.9%** |
| L4 全绿 | L2 ∧ L3 | 15/19 = **78.9%** |

单次缺口率 **21.1%**。

### 为什么用「多班次」而不是「单次长重试」

两种做法都能把缺口率压下去，但成本不同：

| 做法 | 日成功率 | 单次执行时长 | 最坏配额 | 失败形态 |
|---|---|---|---|---|
| 单次 + G3 内部重试 2 次 | 99.1% | 可能挂 5–10 分钟 | 3 | 一次执行卡很久，中途崩了全丢 |
| **3 班次 × 短重试（本方案）** | **99.1%** | **每次 ≤2 分钟** | 7（通常 1） | 某班次崩了，下一班补 |

3 班次都失败的概率 = (1 − 0.789)³ ≈ **0.9%**，与「单次内部重试 2 次」等价，但**执行更短、失败可隔离**。

代价是最坏配额从 3 涨到 7。用 **early out** 把这个代价收回来：一旦某班次达标，后续班次直接退出，正常日仍只消耗 **1 次**。

## 1. 编排（每班次 7 步，顺序不可换）

```
⓪ 早退判定      node scripts/should_run.js        → 退出码 10 就结束，后面全不做
                 ↓ 退出码 0 才继续
① 取原文        node scripts/wendao.js --from 阿勒泰 --to 深圳 --date 2027-01-03 --save out/fare-watch/raw
                 ↓ raw/<ts>.txt
② 抽取          subagent 按 references/wendao-extract-contract.md 产出 extracted/<ts>.json
                 ↓
③ 校验+写盘     node scripts/validate_extract.js --latest
                 ↓ 通过才写 fares.csv / runs.jsonl / latest.md
④ 缺口比对      node scripts/build_baseline.js --check
                 ↓ 退出码 1 = 覆盖不足 → 记下缺口，交给下一班次
⑤ 事后审计      node scripts/verify_fares.js --at "<本次时间戳>"
                 ↓
⑥ 汇报          含缺口清单 + 各闸门状态 + 本班次是否达标
```

**⓪ 必须在最前面，且必须是脚本判定。** LLM 记不住「今天跑过没有」，也不该靠它记。

**②③ 分离是核心**：抽取只产 JSON，校验脚本零判断。JSON 不合格就重跑 ②，不碰主表。

## 2. 四道闸门（每班次内）

| 闸门 | 判据 | 失败处置 | 班次内重试 |
|---|---|---|---|
| **G1 传输** | 命令退出码 0 且原文非空 | 等 30s / 90s / 180s 重试 | **3** |
| | 退出码 2 = 配额 | **不重试**，直接报「今日配额不足，跳过」 | 0 |
| | 退出码 3 = 鉴权 | **不重试**，提示 `node scripts/doctor.js --probe` | 0 |
| **G2 抽取** | JSON 合法 + schema 通过 + `schemes.length ≥ 10` | 重跑 subagent（**换 prompt 变体**，见 §4） | **1** |
| **G3 覆盖** | `coreHit ≥ 4/5` | **不重试**，记入主表后**交给下一班次**（见 §2.5） | **0** |
| **G4 证据** | `verify_fares.js` 硬证据 100% | **不重试**，JSON 进 `quarantine/`，报人工 | 0 |

**单班次配额上限**：1 + 3 + 1 = **5 次**（最坏）；正常 **1 次**。

> G3 不设班次内重试是刻意的：塌陷是随机的（21%），但同一次执行内连续重问，命中率并不会更好——
> 它更可能是「问道此刻对这个航线就是没库存」，等两小时再问才有意义。
> **把重试放在时间维度上，而不是放在同一次执行里。**

## 2.5 多班次调度与 early out

每天调度 **3 次**：`09:00 / 12:00 / 16:00`（依据见 §6）。

### 每个班次的第一件事

```bash
node scripts/should_run.js
```

| 退出码 | 含义 | 动作 |
|---|---|---|
| **10** | 今日已有**达标成功** | **立即早退**：不查询、不写盘、只回一句「今日已完成，跳过」 |
| 0 | 今日无记录，或有记录但未达标 | 继续执行 §1 的六步 |
| 2 | 台账损坏，无法判定 | 按需要执行处理（继续） |

### 达标的定义（三者同时满足）

- `state = ok`
- `schemes ≥ 10`
- `coreHit ≥ 4/5`

### 三种终态

| 情况 | 是否写主表 | 是否早退后续班次 |
|---|---|---|
| **达标**（coreHit ≥4/5） | 写 | **是** |
| **部分**（有数据但 coreHit <4/5） | **写**（数据是真的，缺口在 latest.md 里列出） | **否**，下一班次继续补 |
| **失败**（G1/G2 用尽） | 不写（或只写 runs.jsonl 一行 failed） | **否**，下一班次继续 |

> 部分成功也写主表，是因为**它拿到的那部分是真的**，丢掉浪费；不早退，是因为还缺东西。
> 一天下来主表里可能有 1–3 个不同时间戳，那是**同一天不同时点的快照**，不是重复数据。

### 配额账

| 场景 | 消耗 |
|---|---|
| 第一班就达标（约 79%） | **1 次**，后两班早退 |
| 第一班部分成功、第二班达标（约 17%） | 2 次 |
| 三班都部分成功（约 3%） | 3 次 |
| 三班都失败（约 0.9%） | ≤ 7 次 |

**early out 是这套方案能每天跑 3 次而不浪费配额的关键。** 没有它，日耗会从 1 次变成 3 次。

## 3. 失败恢复

### 3.1 传输失败（G1 用尽）

- 台账写 `state: failed`，`note` 记退出码
- **不要用昨天的数据顶替今天**，也不要改成飞常准（要积分，须先问用户）
- 汇报只说一句：「今日问道不可用（退出码 N），无数据」

### 3.2 抽取失败（G2 用尽）

JSON 不合格 → 落 `quarantine/<ts>.json`，主表不动。汇报附上校验器给的**具体错误行**（缺哪个字段、哪个航班号不在原文）。

### 3.3 覆盖不足（G3 未过）

**默认动作：结束本班次，等下一班。** 不做定向补问，不重跑——塌陷是时间性的，等两小时更有用。

**例外：如果这是当天最后一班（16:00）且 coreHit < 4/5**，才启动定向补问：

```bash
node scripts/wendao.js --query "2027年1月3日阿勒泰飞深圳，有没有 9C7142 接 9C7680 经兰州中转的方案？票面价多少？只要这一个方案，报出行程和价格就行。" --save out/fare-watch/raw
```

- 定向问题更具体，命中率高于全量问（实测全量问会漏掉最便宜档）
- 每次只补一个方案，**最多补 2 个**
- 补回来的数据走同一套 ②③④，**不许直接手写进 CSV**
- 补完仍不足 → 如实汇报缺口，不再纠缠

### 3.4 证据失败（G4）

- 硬证据失败 = 编造或串价，**整批拒绝**，不写主表
- 只写 `runs.jsonl` 一行 `state: rejected`，附失败条数
- 汇报里列出失败明细，由人决定是重跑还是放弃

### 3.5 部分成功

主表写进去的那部分照常写，**缺口在 `latest.md` 和汇报里显式列出**。绝不允许「静默缺几条」。

## 4. G2 重试用的 prompt 变体

第一次抽取用契约 §3 的标准 prompt。若 JSON 不合格，第二次改用下面这个（**只换措辞，规则不变**）：

```
上一轮你产出的 JSON 没能通过 schema 校验，原因：<粘贴校验器报错>

请重做一次，特别注意：
- flights 必须是数组（如 ["9C6620","9C6166"]），不是 "9C6620+9C6166" 字符串
- segments 的数量必须等于 flights 的数量，且 segments[k].flight 必须等于 flights[k]
- 每个方案必须有 evidence 字段（原文片段，≤120 字）
- 抽不出来的写进 unparsed，不要为了凑数编造

只输出 JSON。
```

**变体只针对 schema 违规，不改抽取规则。** 规则出问题（比如城市判错）不靠换 prompt 解决，靠 runbook 补条款。

## 5. 汇报格式（固定五项）

1. **闸门状态**：`G1 ✓ / G2 ✓ / G3 ✗(2/5) / G4 ✓`
2. **数据**：N 条 / coreHit x/5 / 直飞 n 条 / 最低含税 ¥X
3. **缺口**（每天模式最重要的字段）：本次未返回的 active 方案清单，逐条列「方案 / 城市 / 历史价 / 最后出现时间」
4. **价格**：最低 3 条 + 与上次同方案比（覆盖不足就写「不可比」）
5. **异常**：抽取器的 warnings、证据审计结果、占位航班号

## 6. 班次时间选择

实测 19 批的覆盖分布：

| 时段 | 覆盖 |
|---|---|
| 02:07–06:16 | 5/5 满覆盖 |
| 08:20 / 09:30 | 5/5 满覆盖 |
| 10:34–12:39 | 5/5 满覆盖 |
| 14:44 / 15:46 | 4/5 |
| 16:48 / 17:51 | 5/5 满覆盖 |
| **13:41** | **2/5 ⚠** |
| 18:53 / 19:55 | 3/5 ⚠ |
| 07:18 | 2/5 ⚠ |

→ 选定 **09:00 / 12:00 / 16:00**：

- 09:00 —— 上午满覆盖，且是工作日起点，出问题当天还有时间处理
- 12:00 —— 落在 10:34–12:39 的满覆盖区间内
- 16:00 —— 贴近 16:48 满覆盖，同时给前两班的缺口留了补救窗口

**避开 13:00 前后（13:41 实测 2/5）和 18:00 之后（两批都是 3/5）。**

## 7. 目录约定

| 路径 | 谁写 | 说明 |
|---|---|---|
| `raw/<ts>.txt` | 脚本 | 原文，只增不改 |
| `extracted/<ts>.json` | subagent | 抽取结果，可重跑覆盖 |
| `quarantine/<ts>.json` | 脚本 | 校验失败的 JSON，待人工 |
| `fares.csv` | 脚本 | 主表，只由 `validate_extract.js` 写 |
| `runs.jsonl` | 脚本 | 台账 |
| `latest.md` | 脚本 | 快照 |
| `baseline.json` | 脚本 | 方案基线，`build_baseline.js` 写 |

**人（LLM）不许直接写 `fares.csv`。** 所有写入必须经过 `validate_extract.js`。
这是从「LLM 直写 CSV」改成「JSON + 脚本写盘」的全部意义所在。
